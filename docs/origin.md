TL;DR: Я бы сделал `WarpPocket`, маленькое Windows-приложение на Python + Tkinter, внутри которого работают `wireproxy` и `wgcf`. Пользователь получает один `WarpPocket.exe`: нажимает «Подключиться», приложение поднимает локальный SOCKS5 через Cloudflare WARP, проверяет доступность интернета и запоминает рабочую конфигурацию.

Разрабатывать можно полностью на Fedora 44, а Windows EXE автоматически собирать через GitHub Actions. Без установки Python, WSL, WireGuard, драйверов и без прав администратора.

Но есть важное ограничение: поиск рабочих WARP-эндпоинтов не равен полноценному обходу любого DPI. Поэтому я предлагаю архитектуру, в которой можно развивать транспортный механизм, не переписывая GUI.

## 1. Что удалось выяснить из оригинального скрипта

Я изучил не только [README_ru.md](https://github.com/Viktor45/ros-scripts/blob/main/warp-finder/README_ru.md?utm_source=chatgpt.com), но и исходники:

- [warp-finder.rsc](https://github.com/Viktor45/ros-scripts/blob/main/warp-finder/warp-finder.rsc?utm_source=chatgpt.com)
- [warp-finder-mini.rsc](https://github.com/Viktor45/ros-scripts/blob/main/warp-finder/warp-finder-mini.rsc?utm_source=chatgpt.com)

Оригинальный алгоритм работает следующим образом:

1. Берёт заранее известные диапазоны IP Cloudflare.
2. Выбирает случайный адрес и UDP-порт из заданного списка.
3. Перенастраивает WireGuard peer MikroTik.
4. Проверяет работоспособность туннеля через ICMP.
5. Если туннель работает, оставляет настройки. Иначе повторяет поиск.

В основной версии содержатся 15 IP-префиксов и 54 UDP-порта. В `mini` используются только три префикса `162.159.192.*`, `162.159.193.*` и `162.159.195.*`.

Что стоит перенести: генератор кандидатов, список эндпоинтов, последовательную проверку с ограничением попыток и сохранение успешного результата.

Что стоит изменить: оригинал перебирает кандидатов по одному, использует слабый псевдослучайный алгоритм и считает ICMP-ответ достаточным подтверждением работоспособности. Для Windows-приложения с SOCKS5 этого недостаточно. Нужна реальная проверка HTTPS-запросов через прокси.

Ещё важнее, исходный скрипт предполагает, что WARP-аккаунт и WireGuard-конфигурация уже существуют. В новом приложении эту подготовку необходимо автоматизировать.

## 3. Технологический стек

Python 3.12 + Tkinter/ttk

GUI, управление процессами, поиск стратегий, кеширование и логика приложения. Tkinter уже входит в стандартную библиотеку Python. Для настолько простого интерфейса PySide6 будет избыточным.

[wireproxy](https://github.com/windtf/wireproxy?utm_source=chatgpt.com) v1.1.3

Главный компонент. Реализует WireGuard в userspace и предоставляет SOCKS5 на `127.0.0.1`. Windows-драйвер и виртуальный сетевой интерфейс ему не нужны. SOCKS5 поддерживает TCP CONNECT, но не UDP ASSOCIATE.&#x20;

GitHub



[wgcf](https://github.com/ViRb3/wgcf?utm_source=chatgpt.com) v2.3.1

Неофициальный клиент для регистрации устройства в Cloudflare WARP и получения WireGuard-профиля. Нужен преимущественно при первом запуске. Версия 2.3.1 опубликована 11 октября 2026 года.

[PyInstaller](https://pyinstaller.org/?utm_source=chatgpt.com)

Собирает Python, GUI, библиотеки и оба Windows-бинарника в один исполняемый файл. Во время запуска содержимое распаковывается во временный каталог.&#x20;

### Как работает кнопка «Подключиться»

При первом запуске программа проверяет наличие WARP-профиля. Если профиля нет, после получения согласия с условиями Cloudflare запускает встроенный `wgcf`, регистрирует устройство и создаёт необходимые ключи.

Далее запускается `wireproxy` с локальным SOCKS5-портом и одним из сохранённых эндпоинтов. Python проверяет, что прокси действительно может передавать HTTPS-трафик через WARP.

При последующих запусках регистрация уже не нужна. Приложение сразу использует последний успешный эндпоинт.

Если сохранённый эндпоинт перестал работать, автоматически пробуем резервные варианты. Если и они не работают, запускаем ограниченный поиск новых.

### Как работает кнопка «Найти новую стратегию»

Здесь предлагаю улучшить исходный алгоритм.

Вместо чисто случайного перебора сделать Smart Endpoint Finder.

Сначала проверяются ранее успешные IP:порт, затем известные комбинации из исходного скрипта, затем остальные кандидаты из ограниченного списка.

Для ускорения можно одновременно запускать два-три временных экземпляра `wireproxy`, каждый на своём локальном порту.

Каждый кандидат проходит три проверки:

- WireGuard способен установить связь через конкретный UDP-эндпоинт.
- Через SOCKS5 открывается `https://www.cloudflare.com/cdn-cgi/trace` с подтверждением `warp=on` или `warp=plus`.
- HTTPS-трафик проходит хотя бы к одному независимому ресурсу, не использующему Cloudflare, с резервными тестовыми адресами.

Последний пункт принципиален. Есть открытые сообщения о конфигурациях `wgcf`, где WireGuard handshake работает и Cloudflare отвечает, но соединения с другими сайтами зависают.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

GitHub



После успешного поиска сохраняем не просто первый рабочий вариант, а несколько кандидатов с результатами проверок, задержкой и временем последнего успеха.

Активное подключение при этом не трогаем. Новая стратегия становится предпочтительной при следующем старте. Если текущий туннель уже недоступен, допускается автоматическое переключение.

## 5. Кеш и сохранение настроек

Предлагаю хранить основной кеш в JSON:

```

{
  "schema_version": 1,
  "proxy": {
    "host": "127.0.0.1",
    "port": 25344
  },
  "last_good": {
    "ip": "162.159.192.1",
    "port": 2408,
    "latency_ms": 82,
    "verified_at": "2026-10-18T18:00:00Z"
  },
  "fallbacks": [],
  "search": {
    "max_attempts": 30,
    "concurrency": 3
  }
}

```

Пример структуры, значения соединения условные. Приватные ключи WireGuard сюда не записываются.

Есть один нюанс с портативностью. Сохранять изменяющуюся конфигурацию внутрь самого EXE нельзя. Поэтому один EXE остаётся форматом распространения, а данные создаются при запуске, например здесь:

`%LOCALAPPDATA%\WarpPocket\`

Там будут настройки, WARP-профиль и диагностические логи. Права доступа ограничиваем текущим пользователем, ключи не выводим в логи.

Таким образом, приложение не требует установки, а стратегия сохраняется между запусками. Для настоящего USB-portable режима позже можно добавить хранение данных рядом с EXE, но тогда появятся дополнительные файлы.

## 6. Самая важная техническая проблема: WARP и DPI в 2026 году

Здесь нельзя обещать невозможное.

Официальный клиент Cloudflare сегодня преимущественно использует MASQUE, а не WireGuard. Более того, официальная реализация Local Proxy перешла на MASQUE.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://developers.cloudflare.com\&sz=32)

Cloudflare WARP client docs

+1



Наше решение с `wgcf + wireproxy` использует сторонний WireGuard-клиент и не обязано повторять поведение официального WARP.

Это означает:

Если провайдер блокирует только некоторые адреса и порты WARP, поиск альтернативных эндпоинтов действительно может помочь.

Если блокируется сам WireGuard или весь подходящий UDP-трафик, перебор IP и портов не гарантирует результата. Понадобится другой транспортный механизм, и одного изменения MTU или UDP-порта может оказаться недостаточно.

Поэтому я бы сразу заложил внутренний интерфейс `TransportBackend`, но в первой версии реализовал только `WireGuardBackend`. Это позволит исследовать MASQUE или другие совместимые транспорты в будущем без переделки GUI и кеша.

Также следует предусмотреть ошибку регистрации WARP. `wgcf` зависит от неофициально используемого API Cloudflare, поведение которого менялось. Нужен резервный способ импортировать собственный совместимый WireGuard-профиль.

## 7. Разработка на Fedora 44 и сборка Windows EXE

Это решаемо, причём довольно чисто.

PyInstaller не является полноценным кросс-компилятором: обычный запуск на Fedora создаст Linux-бинарник, а не Windows EXE. Официальная документация рекомендует выполнять сборку на целевой платформе.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://pyinstaller.org\&sz=32)

PyInstaller 6.22.2 documentation



Я бы использовал следующую схему:

Fedora 44

Разработка Python, тестирование GUI, поиск стратегий на Linux, запуск Linux-версий wireproxy и wgcf

GitHub Actions · windows-latest

Установка Windows Python, получение закреплённых версий зависимостей, проверка SHA256, запуск PyInstaller, тесты

WarpPocket.exe

Один файл для передачи пользователю Windows 10 x64

Команда сборки внутри Windows runner:

```

python -m PyInstaller --noconfirm --clean --onefile --windowed --name WarpPocket --add-binary "vendor/wireproxy.exe;." --add-binary "vendor/wgcf.exe;." src/main.py

```

До выполнения команды CI должен скачать и проверить указанные Windows-бинарники.

Для запуска встроенных файлов Python использует путь к распакованным ресурсам PyInstaller. При штатном закрытии процесса временные файлы удаляются.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://pyinstaller.org\&sz=32)

PyInstaller 6.22.3 documentation



Для Windows 10 сначала ориентируемся на x64. Финальную сборку обязательно тестируем на реальной Windows 10 или в VM: успешное выполнение Windows CI не доказывает совместимость со всеми версиями Windows 10.

Wine на Fedora тоже возможен, но GitHub Actions как основной механизм будет проще сопровождать.

## 8. Завершение всех процессов при закрытии

Это необходимо реализовать отдельно, а не надеяться на обычный `subprocess.terminate()`.

Для Windows я бы использовал Job Objects с флагом `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, через стандартный Python `ctypes`.

Все временные экземпляры `wireproxy`, активный сервер и `wgcf` находятся под управлением приложения. При штатном выходе сначала завершаем процессы, затем закрываем Job Objects. При аварийном завершении основного процесса механизм Job Objects помогает предотвратить оставшиеся фоновые серверы.

В стандартной работе приложение не должно изменять системные маршруты, глобальные настройки прокси или брандмауэр Windows.

Прокси слушает исключительно `127.0.0.1`, не `0.0.0.0`.

Я бы разделил разработку на четыре последовательных этапа.

Этап 1. R&D: доказать работоспособность

На Fedora автоматически получить WARP-профиль, запустить `wireproxy`, поднять SOCKS5 и проверить HTTP/HTTPS через туннель. Затем проверить смену IP:порт. До успешного результата GUI не писать.

Этап 2. Логика подключения

Реализовать кеш стратегий, параллельный поиск, проверку работоспособности, отмену поиска и управление жизненным циклом процессов. Покрыть тестами с подменёнными сетевыми ответами.

Этап 3. Минималистичный GUI

Добавить Tkinter, большую кнопку, статус, копирование адреса прокси и кнопку поиска. Сетевые операции должны исполняться вне UI-потока.

Этап 4. Windows portable release

Добавить GitHub Actions, упаковку зависимостей, лицензии компонентов, автоматические тесты запуска и остановки, затем проверить всё на Windows 10 и в сети с реальными DPI-ограничениями.

Критерий готовности MVP: пользователь на чистой Windows 10 запускает один EXE, получает работающий SOCKS5, может сохранить новую стратегию, а после закрытия не остаётся фоновых процессов и открытого порта. Неудачная регистрация или отсутствие доступных эндпоинтов должны объясняться понятным сообщением, без ложного статуса «Подключено».

Ещё важно проверить отсутствие DNS-утечек в выбранном браузере. Пользователю понадобится SOCKS5 с удалённым разрешением имён. Это прокси для выбранных программ, а не системный VPN.

## 10. Моя рекомендация

Я бы начинал именно с `Tkinter + wireproxy + wgcf + PyInstaller + GitHub Actions`. Это позволяет реализовать задумку с минимальным объёмом собственного кода и сохранить возможность расширения транспортного движка.

Однако главный технический риск проекта не Windows, Python или упаковка зависимостей. Это стабильность стороннего WARP/WireGuard-подключения в 2026 году, особенно регистрация аккаунтов и доступ к ресурсам за пределами сети Cloudflare.

Поэтому первый результат, который стоит поручить LLM-агенту, это не красивое окошко, а воспроизводимый E2E-тест: новая регистрация WARP → запуск SOCKS5 → успешный запрос через туннель → смена эндпоинта → повторный успех.

Если этот сценарий стабильно проходит на Fedora и в целевой сети, остальная часть приложения уже вполне стандартная инженерная работа.
