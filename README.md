# WarpPocket

Небольшой SOCKS5-клиент Cloudflare WARP для выбранных приложений: **один нативный Windows EXE на Go с Gio UI**, без установки Python, WireGuard, драйверов или прав администратора.

## Архитектура

Backend, GUI, WARP API, подготовка исходников, smoke и публикация написаны на Go. Python/Tkinter/PyInstaller, отдельные `wireproxy.exe`/`wgcf.exe`, WebView и извлечение helpers не используются. Светлый Crayon-интерфейс нарисован средствами Gio; шрифты с кириллицей, CA-сертификаты и лицензии встроены в EXE.

**Один файл не означает один процесс.** GUI запускает собственный EXE в закрытом режиме `--engine`: один primary и не более одной последовательной probe-проверки. На Windows workers принадлежат Job Objects с kill-on-close, назначенным атомарно при создании; на Linux используются отдельные process groups. Это сохраняет очистку при закрытии и аварии GUI без извлекаемых бинарников.

Сетевое ядро — закреплённые исходники wireproxy/WireGuard с патчами `reserved-support+ordered-dns+split-routing`. WARP `Reserved` подставляется в исходящие сообщения; зеркалированное сервером поле очищается перед разбором входящих. GUI не меняет маршруты, DNS, firewall или глобальный прокси ОС.

План миграции и проверяемые результаты: [Go/Gio goal](docs/goals/2026-10-19-warppocket-go-gio.md). Реальный Go network gate переиспользовал существующие профили: 58 HTTPS-запросов без обрыва во время 15-секундного probe-поиска, один primary-stream, максимум два engine-workers; DIRECT/IP-only маршрутизация, неизменность профилей и cleanup подтверждены. Нативный Windows CI проверяет работу на Server 2022, а не удостоверяет отдельную приёмку на чистой Windows 10.

Не считать открытый SOCKS-порт доказательством подключения: проверка требует `warp=on/plus` и независимого HTTPS-ресурса. Это не системный VPN и не гарантия обхода DPI.

## Запуск приложения

### Готовый Windows EXE

**[Скачать WarpPocket.exe](https://github.com/0FL01/WarpPocket/releases/download/rolling/WarpPocket.exe)** — прямая ссылка на последний успешно опубликованный EXE. [Страница rolling-релиза](https://github.com/0FL01/WarpPocket/releases/tag/rolling).

Для запуска нужны только сам EXE и обычная учётная запись Windows x64: устанавливать Python, Go, WireGuard или драйверы не нужно. Распаковка не требуется: в релизе прикреплён **только `WarpPocket.exe`**, без ZIP, checksum-файлов и smoke-отчётов. Приложение не подписано; SmartScreen может показывать предупреждение об неизвестном издателе.

Каждый push в `master` сначала проходит Linux/Windows tests, сборку и packaged smoke. Только после их успеха job `Publish rolling EXE` обновляет тег `rolling`, описание и EXE в одном постоянном релизе. Pull request, push в другую ветку и ручной запуск workflow ничего не публикуют. Публикации выполняются последовательно; поздно завершившаяся старая сборка не откатывает более новую. Внутренние Actions-артефакты и безопасные smoke-отчёты остаются в CI, а не прикрепляются к релизу.

### Из исходников

После подготовки и сборки из раздела ниже:

```sh
build/warppocket-go --data-dir "$HOME/.local/share/warppocket-e2e"
```

Без `--data-dir` используется системный каталог данных. Согласие с условиями Cloudflare запрашивается в интерфейсе перед первой регистрацией. Для поиска при активном подключении нужен отдельный профиль `probe`: приложение объясняет это отдельно и регистрирует вторую идентичность только после подтверждения.

Поиск проверяет не больше 30 кандидатов за 180 секунд и не переключает активное соединение. Лучший результат сохраняется для следующего подключения; при нём endpoint заново проверяется основным профилем. «Отменить» отменяет подключение; «Отключиться» доступна и во время фонового поиска. Без подключения поиск последовательно использует существующий primary-профиль. Ошибка записи кеша показывается отдельно и не выдаётся за успешное сохранение.

### Автоматическое восстановление и keepalive

После **первого проверенного подключения** приложение само восстанавливает потерянный WARP: отменяет и дожидается probe-поиска, останавливает старый primary и проверяет замену на прежнем **`127.0.0.1:25344`**. В интерфейсе — «Восстанавливаем соединение…» и доступная кнопка «Отключиться». Она, как и закрытие окна, отменяет дальнейшие попытки. Первоначальное неудачное подключение остаётся одноразовым: автоматическая сессия до первого подтверждённого успеха не начинается.

Если подключение дважды не прошло периодическую HTTPS-проверку, сначала пробуются другие существующие WARP endpoint. После падения самого engine прежний endpoint допускается первым один раз: падение процесса не доказывает недоступность адреса. Очередь ограничена 30 кандидатами, один цикл — 180 секундами; следующий цикл продолжает непроверенный хвост, а не повторяет каждый раз начало. Между циклами — отменяемые паузы 2/5/10/20/30 секунд, далее по 30. Кратковременный reconnect не сбрасывает очередь и паузы: нужны две последовательные успешные периодические проверки одного primary. Нет нового транспорта, DIRECT fallback, новой идентичности, регистрации или повторного получения профиля через API.

Монитор ждёт 30 секунд **после завершения** проверки, требует два последовательных сбоя, а сама проверка может занять до 30 секунд. Обнаружение потери поэтому может занять около двух минут; 180 секунд — бюджет одного цикла, а не обещание восстановить сеть за три минуты. При недоступности всех WARP endpoint попытки продолжаются с паузами до отмены пользователем. Занятый чужим процессом порт, локальная ошибка запуска/конфигурации или неподтверждённая очистка — терминальная ошибка, а не повод запускать ещё один engine.

**«Без нажатий» не означает сохранение старых TCP-соединений.** При остановке engine они обрываются; после восстановления доступны новые подключения, а повтор старого запроса зависит от клиентского приложения. Исправный primary не заменяется при обычном probe-поиске.

Новые профили, сгенерированные приложением, получают **`PersistentKeepalive = 25`** — встроенный WireGuard keepalive, не отдельный heartbeat-процесс. Существующие и импортированные значения, включая отключённый `0`, сохраняются; runtime не подменяет их и миграционная перезапись не нужна. Keepalive помогает поддерживать NAT-состояние, но не заменяет проверку и восстановление соединения. План и доказательства: [autorecovery goal](docs/goals/2026-10-19-warppocket-autorecovery.md).

## Разработка

Закреплены **Go 1.26.9** и **Gio/Gio-x v0.10.3**. Для Windows работает `CGO_ENABLED=0`; Gio использует системные Win32/Direct3D/OpenGL библиотеки, а не устанавливаемый GUI-runtime. Нативной Linux-сборке нужны EGL/GLES, X11/Wayland, xkbcommon, Xcursor/Xfixes; в headless CI — Xvfb и Mesa. Python для сборки, запуска, тестов и публикации не нужен.

Сначала подготовьте закреплённые Go-исходники. Команда из независимого tools-модуля проверяет SHA256 архива, патчит изолированные копии в `build/deps`, выполняет нативные DNS/routing/sandbox/worker-тесты и только после успеха устанавливает локальные модули. Глобальный module cache не патчится. Оба `replace` в корневом `go.mod` указывают на эти копии; поэтому подготовка выполняется **до** команд корневого модуля.

```sh
go -C tools run -mod=readonly ./cmd/prepare
go -C tools test -mod=readonly ./...
go test -mod=readonly ./...
go test -mod=readonly -race ./...
go build -mod=readonly -trimpath -ldflags='-s -w' -o build/warppocket-go ./cmd/warppocket
```

Windows x64 (PowerShell):

```powershell
go -C tools run -mod=readonly ./cmd/prepare
go -C tools test -mod=readonly ./...
go test -mod=readonly ./...
$env:CGO_ENABLED = '0'
go build -mod=readonly -trimpath -ldflags='-s -w -H windowsgui' -o dist/WarpPocket.exe ./cmd/warppocket
.\dist\WarpPocket.exe
```

`-mod=readonly` указан намеренно: `vendor/` содержит metadata и notices, а не Go vendoring tree. Версии зависимостей фиксируются `go.mod`/`go.sum`, исходники engine — `vendor/wireproxy-build.json`; зависеть от неявного `-mod=vendor` нельзя.

Перед сборкой выполняются Go-тесты DNS-политики в отдельном модуле `wireguard-go/tun/netstack` и routing/sandbox/worker-тесты wireproxy — на ОС раннера даже при cross-build. В них есть A/AAAA, отрицательные ответы, fallback, отмена, общий UDP/TCP deadline, настоящий SOCKS CONNECT и импортируемый engine-entry. Неуспех gate останавливает подготовку и публикацию. Тестовые Go payloads хранятся как `tools/internal/prepare/payload/*.go.txt`, а не как конфликтующие пакеты в корневом модуле.

Нативные screenshot-тесты Crayon (восемь вариантов, включая Connecting + Recovering, при 100/125/150% DPI — 24 кадра):

```sh
LIBGL_ALWAYS_SOFTWARE=1 xvfb-run -a go test -mod=readonly -tags guirender ./internal/ui -run TestRenderedCrayonStatesAndDPI -count=1
```

### Сборка и offline smoke EXE

На Windows после сборки:

```powershell
go -C tools run -mod=readonly ./cmd/smoke --exe ../dist/WarpPocket.exe --out ../build/go-smoke --source-root ..
```

Smoke использует синтетический профиль и UDP endpoint `127.0.0.1:9`: не регистрирует WARP и не обращается в интернет. Проверяются реальные Gio frames, встроенные CA/лицензии, тот же EXE как engine, SOCKS-handshake, нативный clipboard, выбор и импорт тестового файла, отмена второго picker при закрытии окна и штатная очистка. Затем драйвер завершает **только GUI PID** и проверяет остановку engine и закрытие порта **до** аварийной очистки safety-job. Нет PyInstaller outer-launcher; убийство всего дерева не засчитывается как доказательство. EXE запускается один из пути с пробелами и кириллицей, без соседних runtime-файлов. Безопасные JSON-отчёты остаются только внутренними CI-артефактами.

На Linux можно отдельно выполнить `build/warppocket-go --smoke build/go-smoke-linux/graceful.json` под X11 или Xvfb, как в CI. Если локальный Wayland-композитор зависает в EGL, проверенный запуск через доступный X11: `WAYLAND_DISPLAY=warppocket-no-such-display LIBGL_ALWAYS_SOFTWARE=1 build/warppocket-go --smoke build/go-smoke-x11/graceful.json`. Переменные действуют только для этой команды; системные настройки и стандартные renderer-fallbacks приложения не меняются. Полный внешний crash-driver предназначен для Windows.

Обычный `go test -mod=readonly ./internal/backend` на Linux и Windows также проверяет Controller + настоящий Manager/Backend с синтетическим SOCKS-процессом: выход принадлежащего приложению primary → новый живой PID на порту 25344 → сохранение проверенного worker после прежнего trial-deadline → очистка. Интернет и API для этого не нужны.

Для отдельной приёмки на чистой Windows 10 x64 нужны запуск EXE без установленных Python/WireGuard и без повышения прав, реальный HTTPS через SOCKS5, поиск при непрерывном primary-трафике, повторное подключение и очистка после закрытия. Пока такой среды для проверки не было; результат Server 2022 CI не выдаётся за этот тест.

## Реальный сетевой gate: только явно

**Регистрация передаёт данные Cloudflare и означает принятие [условий](https://www.cloudflare.com/application/terms/).** В GUI согласие для primary/probe раздельное. Обычный CI никогда не регистрирует устройства. Опциональный network test использует только уже существующие отдельные профили с `Reserved` и запрещает любые вызовы API, в том числе регистрацию.

```sh
WARPPOCKET_E2E_DATA="$HOME/.local/share/warppocket-e2e" \
WARPPOCKET_E2E_EXE="$PWD/build/warppocket-go" \
go test -mod=readonly -tags network ./internal/acceptance -v -count=1 -timeout=11m
```

Нужен отдельный приватный data-dir с уже созданными primary/probe. Test сначала проверяет настоящее HTTPS через SOCKS/WARP, непрерывный HTTPS-stream во время probe и сохранность работающего primary. DIRECT доказывается исходящим TCP-сокетом именно engine-процесса; запросы к тому же numeric IP остаются в WARP. Затем тест завершает только принадлежащий приложению primary и требует автоматического восстановления: другой живой PID, тот же порт 25344, новый полный HTTPS healthcheck, максимум один primary и один probe. Старый TCP-stream не считается пережившим restart. Во всём сценарии запрещён API, байты аккаунтов/профилей неизменны, а процессы/config/порт очищаются. Безопасный `autorecovery-gate-2026-10-19.json` пишется в приватный data-dir, не в release. Общий timeout учитывает последовательные сетевые бюджеты; производственные таймауты ради теста не сокращены.

Обычное приложение переиспользует сохранённые профили/аккаунты. Перед новым регистрационным POST записывается `registration.pending`: при неоднозначном результате повторная регистрация автоматически не делается. Валидный полученный аккаунт сохраняется до генерации профиля. Не удаляйте аккаунты/marker ради бесконечных регистраций. При блокировке WireGuard/UDP замена GUI не решит транспортную проблему.

## Данные и приватность

Обычный каталог приложения:

- Windows: `%LOCALAPPDATA%\WarpPocket`;
- Linux: `$XDG_DATA_HOME/warppocket`, иначе `~/.local/share/warppocket`.

Профили, аккаунты и схема-1 кеш прежней Python-версии переиспользуются без миграционной перезаписи; проверено по исходным байтам. `--data-dir` позволяет использовать отдельный каталог. Instance lock совместим с прежней версией; файл `.instance.lock` не удаляется после освобождения блокировки.

```text
settings.json                  # только endpoint, роль, время, HTTPS-задержка
profiles/primary/              # account.toml и нормализованный profile.conf, секреты
profiles/probe/                # отдельная идентичность
run/                           # приватные временные конфиги
logs/                          # ограниченные собственные диагностические события
```

Windows-каталог защищён DACL текущего пользователя; на Linux каталоги `0700`, секретные файлы `0600`. Кеш записывается атомарно. Повреждение кеша не затрагивает профили; неизвестная версия кеша не перезаписывается. Сырой вывод engine не сохраняется: он может содержать ключи и токены.

Импорт принимает только нормализованный single-peer WireGuard-профиль: ключи, адреса, DNS-IP, полный IPv4-маршрут, endpoint, MTU, необязательные keepalive/PSK и `Reserved` (три байта 0..255; нужен для WARP-совместимых профилей). Дополнительные listeners/peers, hooks, `WGConfig` и переменные окружения запрещены. Импорт выполняется только при остановленных операциях; исходный текст никогда не передаётся helper напрямую.

Разные локальные SOCKS-порты **не изолируют одинаковые WireGuard-ключи**. Не используйте импортированную идентичность одновременно в другом клиенте.

## SOCKS, split-routing и DNS

Адрес основного прокси: `127.0.0.1:25344`, SOCKS5. Например, в Firefox нужен SOCKS v5 и флажок удалённого DNS через SOCKS. В requests используется `socks5h`, а не `socks5`. Системные маршруты, глобальный прокси и firewall приложение не меняет.

### Жёстко заданная маршрутизация TCP

Встроенный engine выбирает маршрут по имени назначения из SOCKS5; в интерфейсе это обозначено строкой **«RU/РФ/SU и VK — напрямую; остальное — WARP»**. Через **DIRECT** идут:

- домены внутри зон `.ru`, `.su`, `.рф` (IDNA: `.xn--p1ai`), включая их поддомены; сами имена TLD `ru`, `su`, `рф`/`xn--p1ai` под правило не попадают;
- корневые имена и поддомены `vk.com`, `vkontakte.com`, `vk.cc`, `vk.link`, `vk.me`, `userapi.com`, `vk-cdn.net`, `vkuser.net`, `vkuseraudio.com`, `vkuseraudio.net`, `vkuservideo.com`, `vkuservideo.net`, `vkuserlive.com`, `vkuserlive.net`.

Совпадение идёт по границе доменных меток: похожие имена вроде `notvk.com` и `vk.com.example.org` не входят в список. Все остальные домены и **буквальные IP-адреса** идут через **WARP**. Политика встроена в helper: новых настроек, PAC-файлов и сервисов нет. Она применяется при следующем запуске helper'а, не меняя уже работающие primary/probe.

DIRECT означает **только исходящее TCP-соединение через сетевой стек ОС**, а не прямой DNS: **все DNS-запросы имён назначения, включая DIRECT, продолжают идти через встроенную цепочку внутри WARP**. Перед прямым соединением полученные адреса проверяются: локальные/loopback, приватные, link-local, non-unicast и CGNAT отклоняются. При ошибке выбранного маршрута переключения на другой нет: DIRECT не переходит на WARP, а WARP — на DIRECT. **На DIRECT-сайтах виден реальный внешний IP вашего подключения, а не IP WARP.**

На Linux файловая изоляция Landlock и точный список разрешённых listener-портов сохраняются. Для SOCKS-helper разрешён необходимый исходящий TCP; выбор разрешённых DIRECT-доменов и публичного numeric IP выполняет описанный маршрутизатор, поскольку Landlock не умеет фильтровать по hostname. Прочие upstream-конфигурации без SOCKS сохраняют исходные ограничения connect.

Клиент должен передавать **hostname через SOCKS5** (`socks5h`, remote DNS в браузере). Если клиент сам разрешил имя через локальный DNS или DoH и передал только IP, helper не может восстановить домен и оставляет такое назначение на WARP. Отдельный DoH браузера этой политикой не управляется.

wireproxy поддерживает TCP CONNECT, но **не UDP ASSOCIATE**. Для UDP/QUIC, WebRTC, приложений, игнорирующих прокси, и системного трафика гарантий нет: это не системный VPN и не защита от всех утечек браузера.

### DNS внутри WARP

Для DNS имён назначения, переданных через SOCKS5, встроен строгий порядок resolver'ов: **`83.220.169.155` → `212.109.195.93` → `194.87.196.13` → `45.151.102.219` → `9.9.9.9`**. Сначала используется только первый; следующий допускается лишь после сбоя предыдущего, допускающего повторную попытку. Quad9 используется только после четырёх таких сбоев. Порядок координируется для всего lookup, включая A/AAAA: параллельный запрос другого семейства адресов не может раньше времени обратиться к следующему серверу. На один DNS-этап отводится не более **1 секунды**, на весь DNS lookup — не более **5 секунд**. Полученные адреса используются без перехода к следующему DNS. Если адресов нет, корректный отрицательный ответ **NXDOMAIN или NODATA завершает lookup** без перехода дальше; timeout, ошибка транспорта, SERVFAIL или REFUSED разрешают попытку следующего resolver'а. При отказе всех пяти серверов возвращается ошибка — без системного или прямого DNS fallback.

Эта цепочка применяется к временным runtime-конфигам **primary и probe**, в том числе для уже сохранённых и импортированных профилей. Поле DNS в импортированном файле и сохранённом профиле остаётся прежним, но при запуске helper'а заменяется встроенной цепочкой только в runtime-копии; ключи и остальные параметры профиля сохраняются. Изменение действует **при следующем запуске helper'а**, не перенастраивая уже запущенный процесс.

Все DNS-запросы этой цепочки идут **только через WARP**, даже для DIRECT-доменов, и относятся только к проксируемым именам назначения. Системный DNS, bootstrap-разрешение имени самого WARP endpoint до поднятия туннеля и настройки браузерного DoH приложение не меняет. HTTPS healthcheck сохраняет TLS-проверку и `socks5h`, не использует настройки прокси окружения; connect/read timeout — **7/5 секунд**, общий бюджет проверки — **30 секунд**, поиска — **180 секунд**.
